 

UniSchedule 

University Weekly Planner with Google Calendar Sync 

Product Requirements Document 

 

Version 1.0  ·  April 2026 

Status: Ready for Engineering 

Prepared for: Gemini AI Studio Implementation 

 

1. Executive Summary 

UniSchedule is a minimalist, enterprise-grade web application for university students. It allows them to: 

 

Authenticate via Google OAuth 

Browse and select their enrolled lecture courses from a Supabase-backed database 

View a beautiful weekly schedule on the homepage 

Edit their schedule at any time 

Sync automatically all schedule events to their personal Google Calendar 

See an 'Upcoming Lecture' sidebar widget showing the next class of the day 

 

The design language is intentionally inspired by YC-backed enterprise SaaS products such as Attio, Firecrawl, and Linear — minimalist, white-space-driven, Inter font, soft shadows, no gradients, no color noise. Every pixel must feel deliberate. 

 

2. Goals & Non-Goals 

Goals 

Provide a frictionless onboarding: login → pick courses → schedule is live in under 60 seconds 

Reflect all schedule changes in Google Calendar in real-time 

Design a UI that feels premium and trustworthy, not like a student project 

Work entirely in-browser with no native app 

 

Non-Goals 

Mobile app (web only, though must be responsive) 

Grade tracking or academic performance features 

Integration with any LMS (Moodle, Canvas, etc.) at v1 

Push notifications (Google Calendar handles reminders) 

 

3. User Personas 

Primary: The Enrolled Student 

Age 18–26, university student 

Has a Google account (university or personal) 

Wants to avoid manual data entry into Google Calendar 

Values clarity and speed 

 

Secondary: The Organised Student Leader 

Manages club activities alongside academic schedule 

Wants to quickly see conflicts and free windows

5. Supabase Data Schema 

Table: lectures 

This is the master table populated by the university/admin. Students do not modify this table. 

 

id            uuid primary key default gen_random_uuid(), 

course_code   text not null,   -- e.g. 'CS301' 

course_name   text not null,   -- e.g. 'Algorithms & Data Structures' 

professor     text not null,   -- e.g. 'Dr. Elena Vasquez' 

room          text,            -- e.g. 'Building A, Room 204' 

day_of_week   text not null,   -- 'Monday' | 'Tuesday' | ... | 'Friday' 

start_time    time not null,   -- e.g. 09:00 

end_time      time not null,   -- e.g. 10:30 

semester      text not null,   -- e.g. 'Spring 2026' 

department    text,            -- e.g. 'Computer Science' 

color_tag     text             -- optional hex for UI, e.g. '#E8F0FF' 

 

Table: user_schedules 

Maps authenticated users to their selected lectures. 

 

id              uuid primary key default gen_random_uuid(), 

user_id         uuid references auth.users(id) on delete cascade, 

lecture_id      uuid references lectures(id) on delete cascade, 

google_event_id text,   -- returned by Google Calendar API after sync 

created_at      timestamptz default now(), 

unique(user_id, lecture_id) 

 

Table: user_profiles 

Stores Google OAuth tokens needed for Calendar API calls. 

 

id                    uuid primary key references auth.users(id), 

full_name             text, 

avatar_url            text, 

google_access_token   text, 

google_refresh_token  text, 

token_expires_at      timestamptz, 

updated_at            timestamptz default now() 

 

6. Authentication Flow 

User lands on the Landing Page (unauthenticated state) 

User clicks 'Sign in with Google' in the header 

Supabase Auth triggers Google OAuth 2.0 with scopes: openid, email, profile, calendar, calendar.events 

On success, Supabase creates the user in auth.users, stores tokens in user_profiles 

User is redirected to /dashboard (authenticated home) 

If no user_schedules rows yet → show Course Selection Modal immediately 

If user already has a schedule → show the Dashboard directly 

 

Session Persistence 

Supabase handles session refresh automatically 

On page reload, check supabase.auth.getSession() before rendering protected routes

9. Google Calendar Integration 

How it works 

When the user confirms their schedule, for each selected lecture, call POST /v3/calendars/primary/events with a recurring weekly event: 

 

summary: "CS301 — Algorithms & Data Structures" 

location: "Building A, Room 204" 

start.dateTime: "2026-02-03T09:00:00" 

end.dateTime: "2026-02-03T10:30:00" 

recurrence: ["RRULE:FREQ=WEEKLY;BYDAY=MO;UNTIL=20260630T235959Z"] 

reminders.overrides: [{ method: "popup", minutes: 15 }] 

 

Store the returned event.id in user_schedules.google_event_id. 

 

Edit / Remove 

Remove a lecture: DELETE /v3/calendars/primary/events/{eventId}, delete user_schedules row 

Change a lecture: PATCH the existing event, update user_schedules 

 

Token Refresh 

Before any Calendar API call, check token_expires_at in user_profiles 

If expired, call Google's token refresh endpoint using refresh_token 

Update stored access_token and token_expires_at in Supabase 

 

10. Edit Schedule Flow 

Accessed via 'Edit Schedule' button. Reuses the Course Selection UI (/select-courses) with all currently enrolled courses pre-checked. 

 

Diff Logic 

previous = current user_schedules lecture_ids 

next = newly selected lecture_ids 

to_add = next − previous → create Google Calendar event, insert user_schedules row 

to_remove = previous − next → delete Google Calendar event, delete user_schedules row 

Unchanged courses → no API call made

17. Security Considerations 

All Supabase queries use Row Level Security (RLS) — users can only query their own user_schedules rows 

Google OAuth tokens stored in Supabase, never in localStorage 

google_access_token and google_refresh_token columns: RLS policy allows only auth.uid() = id 

Calendar API calls made server-side via Supabase Edge Functions — tokens never exposed to browser 

CSRF: Supabase Auth handles state parameter in OAuth flow 

Rate limiting: Edge Functions implement per-user rate limiting on sync operations 

 

18. Supabase Edge Functions 

sync-schedule 

Trigger: Called when user confirms course selection or edits schedule. 

Input: { to_add: lecture_id[], to_remove: { lecture_id, google_event_id }[] } 

Fetch user's Google tokens from user_profiles 

Refresh token if needed 

Create/delete Calendar events via Google API 

Update user_schedules in Supabase 

Return { success: boolean, errors: [] } 

 

get-upcoming 

Trigger: Called on dashboard load and every 5 minutes. 

Input: { user_id } 

Fetch user's user_schedules joined with lectures 

Filter to today's day_of_week 

Sort by start_time ascending 

Return lectures happening after now()

20. Design Anti-Patterns to Avoid 

The following must NEVER appear in the UI: 

 

Blue accent colours (no Bootstrap blue, no link blue, no primary-500) 

Purple or gradient anything 

Generic sans-serif fallback styling 

Heavy drop shadows (keep all shadows extremely soft) 

Animated backgrounds, particles, or gradient mesh on marketing page 

Emoji in production UI (landing page or app) 

Success states with green fills — use subtle border changes instead 

Glassmorphism panels, neon glow, dark mode by default 

 

The visual benchmark is: would this feel at home in the Attio, Linear, or Firecrawl product? If yes, proceed.

22. Open Questions for Engineering 

Semester date range: Add a semesters table or hardcode per deployment? 

Time zone: Browser locale or university-specific? Recommend storing UTC and converting client-side. 

Multi-section conflicts: Prevent selection of two sections of same course, or warn only? 

Lecturer changes: Should lecture row updates in Supabase auto-patch Google Calendar events? (Recommend: yes, via DB trigger) 

Holiday handling: If recurring events skip holidays, a holidays table with EXDATE RRULE rules is needed.
